# Degg Crop Image — спецификация

Нода ComfyUI: кадрирование с интерактивной рамкой на теле ноды; рамка может
выходить за изображение (аутпейнт) без второго входа.

- Класс: `DeggCropImage`, отображаемое имя `Degg Crop Image`
- Категория: `My_custom_nodes/Image`
- Выходы: `IMAGE`, `MASK`, `width`, `height` (фактические размеры результата)

## 2. Контракт входов/выходов

| Вход | Тип | По умолчанию | Смысл |
|------|-----|--------------|-------|
| `image` | IMAGE | — | источник (батч `[B,H,W,C]`) |
| `lock_ratio` | BOOLEAN | `true` | удерживать пропорцию при перетаскивании |
| `center_x` | INT ±100000, step 1 | `0` | смещение центра рамки по X от центра изображения, px |
| `center_y` | INT ±100000, step 1 | `0` | смещение центра рамки по Y от центра изображения, px |
| `frame_w` | INT 0…100000, step 1 | `0` | ИТОГОВАЯ ширина результата, px |
| `frame_h` | INT 0…100000, step 1 | `0` | ИТОГОВАЯ высота результата, px |
| `output_size` | STRING (скрыт) | `` | ручной размер результата `Ш,В`; пусто = считать по мегапикселям |
| `aspect_ratio` | COMBO | `free` | протокол: `free,1:1,2:3,3:2,4:3,3:4,16:9,9:16,21:9` |
| `megapixels` | FLOAT 0.1…64 | `2.0` | целевая площадь, 1 MP = 1024² |
| `multiplicity` | INT 8…128, step 4 | `8` | кратность сторон результата |
| `resample` | COMBO | `lanczos` | `lanczos,bicubic,bilinear,nearest-exact` (без перевода) |
| `fill` | COMBO | `transparent` | `transparent,black,white,gray` — фон вне источника |
| `dim_outside` | INT 0…100 | `50` | затемнение вне рамки, только отображение |
| `golden_ratio` | BOOLEAN | `false` | сетка золотого сечения поверх рамки, только отображение |
| `mask` | MASK (опц.) | — | конвенция ComfyUI: **1 = убрать** область, видимая альфа = `1 − маска` |
| `crop_rect` | STRING (скрыт) | полный кадр | `{x, y, w, h}` в долях изображения |

Порядок строк таблицы = порядок виджетов на теле ноды (после превью): `lock_ratio`,
`center_x`, `center_y`, `frame_w`, `frame_h`, `aspect_ratio`, `megapixels`,
`multiplicity`, `resample`, `fill`, `dim_outside`. `image`/`mask` — сокеты,
`crop_rect` и `output_size` скрыты.

`center_x`/`center_y`/`frame_w`/`frame_h` — UI-поля (как `aspect_ratio`/`lock_ratio`):
рамку на сервере считает `crop_rect`, а эти поля её описывают в UI и пишутся
интерфейсом. `output_size` хранит ручной размер результата — без него сервер
считал бы размер только по мегапикселям.

COMBO-значения — протокол: подписи меняются через `getOptionLabel`, значения в
workflow не переводятся.

**Запуск вне интерфейса (API/скрипт).** Фронтенд отправляет серверу значения
всех виджетов сам, поэтому из интерфейса нода всегда «полная». При постановке в
очередь кодом ComfyUI требует перечислить все **обязательные** входы
(`required_input_missing` иначе).

Поэтому обязательными оставлены только те, что реально влияют на результат:
`image`, `megapixels`, `multiplicity`, `resample`, `fill`, `dim_outside`.
Остальные (шесть «интерфейсных» + скрытые `crop_rect`/`output_size`) объявлены
**необязательными** — API их не требует, а их значения по умолчанию корректны.
Подробности и порядок виджетов — §5.0 и §5.0.1.

## 3. Разрешение результата

Повторяет ядро ComfyUI (`comfy_extras/nodes_resolution.py`, «Выбор разрешения»):

```
total = megapixels * 1024 * 1024
scale = sqrt(total / (rw * rh))
width = max(step, round(rw * scale / step) * step)
height = max(step, round(rh * scale / step) * step)
step = max(1, int(multiplicity))
```

- `round` банковский (`py_round`), стороны округляются независимо;
- шаг не клампится внутри функции — диапазон `8…128` задаёт `INPUT_TYPES`
  (старые воркфлоу с меньшим шагом считаются как есть);
- примеры: `16:9 / 2 MP / 8 → 1928×1088`, `1:1 / 2 MP / 8 → 1448×1448`,
  `1:1 / 1 MP / 8 → 1024×1024`, `1:1 / 0.5 MP / 8 → 728×728`;
- плашка в JS показывает фактические `W × H` и фактические MP (1928×1088 = 2.10)
  **в одну строку**, разделённые отступом: `1928 × 1088 px   2.10 MP`.

## 4. Геометрия кадра

`frame_geometry(src_w, src_h, rect, out_w, out_h)`:

1. рамка в долях → пиксельные границы источника, дробные границы
   раскрываются наружу (`floor` / `ceil`), чтобы не терять пиксели;
2. коэффициент `out_w / frame_w_px` (по X) и `out_h / frame_h_px` (по Y);
3. для каждой границы считаются координаты вставки в холст результата;
4. отрицательные координаты рамки = аутпейнт: холст предзаполняется цветом
   `fill`, изображение вставляется поверх.

`render_frames(...)` возвращает `(canvas, mask_out, out_w, out_h)`:

- `mask_out` — 1 внутри рамки, 0 в залитой области (для `transparent`);
- batch: общий размер, одинаковые координаты, каждый кадр обрабатывается отдельно;
- пустой вход → `(empty_image, zeros, 0, 0)`.

Заливка — **фон под изображением** (так же в DOM-редакторе: слой `fill` создаётся
раньше `img`) — внутри кадра картинку не перекрывает.

⛔ `transparent` = **серый RGB (0.5) при нулевой альфе**, а не чёрный: превью,
которое не учитывает альфу, показывало аутпейнт чёрным. Альфа при этом остаётся
нулевой — результат остаётся прозрачным там, где надо.

## 5. DOM-редактор (Nodes 2.0)

### 5.0. Контракт источников истины

| величина | где живёт | кто пишет | кто читает |
|----------|-----------|------------|------------|
| геометрия кадра (доли источника) | скрытый вход `crop_rect` | интерфейс | **сервер** (`parse_rect`) и интерфейс |
| размер результата вручную (px) | скрытый вход `output_size` | интерфейс | **сервер** (`parse_output_size`) и интерфейс |
| размер результата по мегапикселям | `megapixels` + `multiplicity` | пользователь | **сервер** (`output_size`) и интерфейс |
| пропорции кадра | `aspect_ratio` + `lock_ratio` | пользователь | только интерфейс (политика ресайза) |
| центр кадра | `center_x` / `center_y` | интерфейс | только интерфейс (следствие геометрии) |
| итоговый размер | `frame_w` / `frame_h` | интерфейс | только интерфейс (следствие `crop_rect` + MP) |
| параметры результата | `resample`, `fill`, `dim_outside` | пользователь | `resample`/`fill` — сервер, `dim_outside` — только вид |

⛔ `aspect_ratio`, `lock_ratio`, `center_x`, `center_y`, `frame_w`, `frame_h`
сервер **не использует** — это видимые элементы управления редактора, а
машинное состояние лежит в `crop_rect` и `output_size`. Так сделано намеренно:
размер результата (MP) и размер обреза (px источника) — разные величины, и
«размер обреза» из одних `center_x/center_y/frame_w/frame_h` вывести нельзя
(это размер ВЫХОДА, а не высота кадра в источнике).

### 5.0.1. Архитектура редактора

```
СОСТОЯНИЕ (два источника истины)
  state.frac    — геометрия кадра в долях источника   → crop_rect
  state.manual  — ручной размер результата (px) | null → output_size
  (остальное — производное: размер источника, масштаб сцены, смещение, пропорции,
   захваченные пропорции замка, счётчик подавления)
  Служебное: state.imageKey (ключ показанной картинки — «новая картинка?»),
  state.restoring (нода восстанавливается из воркфлоу — рамку не трогаем).

ПРОИЗВОДНЫЕ ВЕЛИЧИНЫ (нигде не хранятся)
  cropPx() / cropRatio() / resultSize() / effectiveRatio() / megapixels() / multiplicity()

ТОЧКИ ЗАПИСИ (ровно две)
  writeWidget(widget, value, { call })  — единственная запись в виджет;
                                         call:false — тихая (значение отражает
                                         состояние, нода не пересчитывается),
                                         call:true — как фронтенд (виджет изменился)
  programmatic(widget, value)          — программная запись с защитой suppress

ОДНА ТОЧКА ПРИМЕНЕНИЯ СОСТОЯНИЯ
  commit() = persistState() + syncViews() + refreshLayoutSize() + layout()

ОПЕРАЦИИ (у каждой — явная политика)
  moveOrResizeCrop(frac)  — мышь; ручной размер подстраивается за кадром
  applyRatioPreset(value)  — пресет пропорций; ручной результат сбрасывается
  setResultSize(w, h)     — ручной размер; пропорции кадра следуют за результатом
  setMegaPixels()         — правка MP; ручной результат сбрасывается
  setFrameCenter(x, y)    — координаты центра кадра
  resetToImage()          — сброс к подключённому изображению: рамка по всему
                             кадру, пропорции и фиксация — его, размер
                             результата = размер изображения. Используется и
                             кнопкой «Сбросить», и сменой картинки.
  loadStateFromWidgets()  — загрузка воркфлоя (сверка устаревшего размера)
  dropStaleManual()       — сверка: ручной размер, разошедшийся с пропорциями
                             кадра, отбрасывается

ОТРИСОВКА
  layout() — чистая: читает состояние, пишет только в DOM (никаких правок
             состояния внутри layout)
```

Правило: **любое изменение состояния идёт через операцию → commit()**. Поэтому
виджеты-виды не могут «разъехаться» с состоянием, а плашка всегда показывает
тот размер, который реально получится.

### 5.1. Правила, которые нельзя нарушать

- ⛔ **Пропорции результата — по ПИКСЕЛЯМ кадра**, а не по его долям:
  `rect.w*src_w : rect.h*src_h` (точно как в Python, `output_size()`). Для
  НЕКВАДРАТНОГО источника доли и пиксели дают разные пропорции: рамка
  1731×974 px (16:9) в долях выглядит как 0.636×0.634 (почти квадрат) → по долям
  получалось 1448×1448 вместо 1928×1088, и UI врал о размере результата;
- ⛔ **Инвариант пропорций**: пропорции кадра и пропорции результата всегда
  совпадают, иначе кадр растягивается. Разошлись (ручной размер остался от
  прошлого воркфлоу) → ручной режим сбрасывается (`dropStaleManual()`), иначе
  MP и пресет пропорций молча игнорировались бы;
- ⛔ **Живая проба обязана покрывать неквадратный источник**: на квадратной
  картинке (`example.png` 768×768) доли и пиксели совпадают, и ошибка «размер по
  долям» принципиально невидима — именно поэтому баг дошёл до пользователя;
- ⛔ **Масштаб сцены фиксируется на `pointerdown`** (`state.drag.view`): рост
  кадра расширяет union → меняется `scale` → следующий `pointermove` считает
  дельту по новому масштабу, и рамка разгоняется до клампа;
- ⛔ **Письмо в виджет — тихое** (`writeWidget(..., { call: false })`): громкая
  запись перезапускает ноду на каждом кадре drag'а. Программная запись с
  callback'ом — только `programmatic()` (там, где виджет меняет сам интерфейс:
  замок, пресет пропорций);
- ⛔ **`layout()` не меняет состояние** — только рисует. Сверка устаревшего
  ручного размера живёт в операциях и в `loadStateFromWidgets()`, а не в
  отрисовке;
- ⛔ **Тестовых хуков в редакторе нет**: наружу отдаются `widget`, `refresh`,
  `layout`, `commit`, `state`. Проба задаёт кадр через `crop_rect` (как делает
  воркфлоу) и перечитывает состояние через `refresh()`;
- ⛔ **Маска — по конвенции ComfyUI**: маска = 1 там, где область надо УБРАТЬ
  (`LoadImage` отдаёт `1 − alpha`), значит видимая альфа = `1 − маска`. Маска лежит
  в координатах ИСТОЧНИКА: её ВЫРЕЗАЮТ по области кадра, а не сжимают в неё
  (иначе маска съезжает). Если размер маски не совпадает с источником (`LoadImage`
  для картинки без альфы отдаёт заглушку 64×64), она приводится к размеру
  источника. Раньше маска трактовалась как альфа (1 = непрозрачно) — это была
  противоположность конвенции ComfyUI: подключённая маска делала выход чёрным;
- ⛔ СЕТКА ЗОЛОТОГО СЕЧЕНИЯ (`golden_ratio`, только отображение, по умолчанию
  выключено) — слой `.degg-crop__grid` между затемнением и рамкой (рамка и
  «уголки» остаются поверх ✓, `pointer-events:none` → drag не ломается ✓).
  Четыре линии: две вертикальные и две горизонтальные, в точках **1/φ и 1−1/φ**
  (0.618 и 0.382) от краёв **текущей** рамки. Позиции пересчитываются при
  каждом изменении размера кадра (`layout()`), поэтому сетка всегда отмечает
  золотое сечение именно текущего кадра и едет вместе с ним. Линии светлые
  (rgba(255,255,255,.6)) с тёмной подложкой (1 px rgba(0,0,0,.35)) — читаются
  и на светлом, и на тёмном;
- ⛔ **Ручной размер — только через `setResultSize()`**: он меняет и результат,
  и пропорции кадра (иначе кадр растянется). Правка координат — только через
  `setFrameCenter()`;
- ⛔ **Кнопка «Сбросить» = `resetToImage()`**, и смена картинки ведёт туда же:
  две разные картинки одного размера тоже сбрасывают рамку (смена определяется
  по ключу превью, а не по размеру).

- `addDOMWidget(..., { hideInPanel: true, hideOnZoom: false })` — панель свойств
  иначе пишет `widget.width` в живой виджет и зажимает контент;
- `computeLayoutSize` возвращает `minHeight`, высота = ширина × соотношение +
  плашка (без `scrollHeight`/`offsetHeight`/`computeSize`);
- превью источника берётся по проводу мгновенно (`p:/o:/i:/n:`), без выполнения
  воркфлоу; смена изображения в upstream-ноде (загрузка в `LoadImage`) приходит
  ДВУМЯ каналами: legacy (`BaseWidget.setValue`, upload-виджет) зовёт
  `source.onWidgetChanged`, Nodes 2.0 (`createWidgetUpdateHandler`) зовёт только
  `widget.callback` и `node.onWidgetChanged` не вызывает. Поэтому обёрнуты оба
  канала: `watchedHandler` на хуке узла и `watchSourceWidgets()` на callback'ах
  виджетов источника (с восстановлением в `detachSource()`);
- смена картинки определяется подменой объекта `app.nodeOutputs[locator]`
  (`sourceOutputsChanged()`), а не ключом/именем файла: перезаливка файла с тем
  же именем не меняет ключ, но `setOutputsByLocatorId` всегда присваивает новый
  объект → принудительный `loadSource({ force: true })` с кэш-бастером;
- зум/пан графа не влияют на координаты: экранные координаты приводятся к
  локальным через `getBoundingClientRect`;
- изменения виджетов (`dim_outside`, `fill`, `megapixels`, `multiplicity`)
  прогоняются через обёртку callback → `layout()`, иначе DOM не перерисуется;
- бар редактора:
  - «Вписать» (`fitFrameFrac`) — равномерный масштаб ТЕКУЩЕЙ рамки
    `s = min(1/w, 1/h)` вверх и вниз до касания ближайших границ + центр;
    пропорции и режим не меняются;
  - «По центру» (`centerFrameFrac`) — только перенос центра рамки в центр
    изображения; размер и пропорции сохраняются, выход за границы разрешён;
  - «Сбросить» — та же операция, что и при подключении картинки
    (`resetToImage`): рамка по всему изображению, а значения ноды принимают
    значения изображения. Подробности — в «Сброс к изображению» ниже;
- «Зафиксировано» (`lock_ratio`) — фиксирует ТЕКУЩИЕ пропорции рамки
  (`state.ratioLock = currentPxRatio()`), а не подставляет пресет из списка:
  при `aspect_ratio='free'` захваченное соотношение (`ratioLock`) имеет приоритет
  над пресетом; `effectiveRatio() = ratio() ?? ratioLock ?? currentPxRatio()`;
  выбор пресета в списке применяет его И включает замок; выбор «Свободные»
  снимает замок (`programmatic(aspectWidget, 'free')`);
  `lock_ratio`/`aspect_ratio` в Python на выход не влияют (выход = `crop_rect`),
  поэтому «Свободно» + захваченное соотношение не нарушает протокол combo;
- ⛔ ПРАВИЛО ВЫБОРА: числовая опция ноды — это НАТИВНЫЙ виджет `INPUT_TYPES`
  (нижние опции, нативный вид, значение ездит в workflow), а НЕ кастомный
  `<input>` внутри DOM-редактора. Кастомный DOM-контрол — только для составных
  значений (несколько полей, свой вид, live-привязка к сцене). Прецедент:
  координаты сначала были кастомным `<input type="number">` — выглядело «не как у
  остальных», не попадало в workflow; переделано в нативные опции;
- координаты — НАТИВНЫЕ опции ноды (`center_x`, `center_y`: INT, шаг 1, диапазон
  со знаком), стоят сразу под виджетом «Фиксация пропорций» и выглядят как
  остальные бегунки ноды (label + `−` + значение + `+`); значения — СМЕЩЕНИЕ
  ЦЕНТРА РАМКИ относительно центра изображения, в ПИКСЕЛЯХ оригинала
  (`frameCenterOffset`/`moveFrameToOffset`);
  - рамка меняется → координаты перезаписываются (`syncViews`), запись ТИХАЯ
    (`writeWidget(..., { call: false })`), иначе каждый кадр drag'а перезапускал
    бы ноду;
  - пользователь правит координату → callback виджета → рамка едет
    (`setFrameCenter` → `moveFrameToOffset`);
  - `center_x`/`center_y` в Python — UI-поля (как `aspect_ratio`/`lock_ratio`):
    рамку считает `crop_rect`;
- РАЗМЕР РЕЗУЛЬТАТА (`frame_w`/`frame_h`) — это ИТОГОВЫЙ размер картинки (те
  же числа, что в плашке и в выходах `width`/`height`), а не размер обреза.
  Два режима, переключаются сами:
  - **по мегапикселям** (обычный): результат = пропорции рамки + MP + кратность,
    поля просто показывают итог;
  - **ручной**: результат = введённое число, округлённое до кратности
    (1333 × 750 при кратности 8 → 1336 × 752);
  - в ручном режиме остальные параметры ПОДСТРАИВАЮТСЯ под введённый размер:
    пропорции рамки приводятся к пропорциям результата (площадь и центр
    сохраняются — как при выборе пресета, иначе кадр растянулся бы), а
    мегапиксели показывают эквивалент результата (`Ш × В / 1024²`);
  - **обратное направление**: выбор пресета пропорций или правка мегапикселей
    сбрасывают ручной режим, и поля снова показывают размер, посчитанный от MP
    (16:9 + 2 МП → 1928 × 1088);
  - ручной размер хранится в скрытом `output_size` (`Ш,В`), поэтому переживает
    перезагрузку воркфлоу и не зависит от точности поля «Мегапиксели» (шаг 0.1);
  - ⛔ ИТОГОВЫЙ РАЗМЕР СЧИТАЕТСЯ ПО ПИКСЕЛЯМ КАДРА (`cropPx()`), а не по его долям:
  пропорции результата = `rect.w*src_w : rect.h*src_h` — ровно как в Python
  (`output_size(rect["w"] * src_w, rect["h"] * src_h, ...)`). Для НЕКВАДРАТНОГО
  источника доли и пиксели дают разные пропорции: рамка 1731×974 px (16:9) в
  долях выглядит как 0.636×0.634 (почти квадрат) → по долям получалось
  1448×1448 вместо 1928×1088, и UI врал о размере результата;
- ⛔ ИНВАРИАНТ: пропорции кадра и пропорции ручного результата всегда совпадают.
    Разошлись (например, ручной размер остался от прошлого воркфлоу, а выбраны
    16:9 и 2 МП) — ручной режим сбрасывается, иначе MP и пресет молча
    игнорировались бы, а кадр растягивался бы. Сверка (`dropStaleManual`)
    выполняется при загрузке воркфлоя и при смене картинки — ДО отрисовки
    плашки (в `layout()` её нет: отрисовка чистая);
  - свободный drag (меняет пропорции кадра) подстраивает ручной размер без
    рывков: ширина сохраняется, высота следует за пропорциями;
- ⛔ СБРОС К ИЗОБРАЖЕНИЮ (`resetToImage`) — одна операция на два случая:
  кнопка «Сбросить» и подключение/смена картинки:
  - рамка = всё изображение (`0,0,1,1`);
  - пропорции — пропорции изображения, фиксация включена на них (пресет не
    подходит: у произвольного изображения своего пресета нет);
  - РАЗМЕР РЕЗУЛЬТАТА = РАЗМЕР ИЗОБРАЖЕНИЯ (в пикселях, округлённых до
    кратности). Задаётся ТОЧНО ручным размером, а не мегапикселями: их шаг 0.1
    дал бы «2728 × 1536» вместо «2720 × 1536»;
  - мегапиксели показывают эквивалент (площадь изображения);
  - ручной размер сброшен — он задавал бы другой результат;
  - ⚠️ этот сброс делает JS-редактор, то есть **только в интерфейсе**. Без
    браузера (API/скрипт) сброса нет, и размер определяется переданным
    мегапикселем — подробности в §8.4.
  Смена картинки определяется по САМОМУ КЛЮЧУ превью (файл), а не по размеру:
  две разные картинки одного размера тоже сбрасывают рамку.
  ⛔ Открытие ВОРКФЛОУ сброса не делает: рамка приходит из `crop_rect`, а связи
  в воркфлое восстанавливаются ПОСЛЕ `onConfigure` — поэтому «восстановление»
  помечено флагом `state.restoring` в состоянии (он живёт до первой загрузки
  картинки), а не аргументом загрузки;
- Shift-модификаторы (в режиме «Свободно»):
  - Shift + перетаскивание ВНУТРИ рамки — движение строго по доминирующей оси
    (`axisDelta`: `|dx| >= |dy|` → горизонталь);
  - Shift + тянутая сторона/угол — ресайз с сохранением текущих пропорций
    (`state.drag.ratio`, снятый на `pointerdown`); замок при этом НЕ включается;
- иконка «?» (`.degg-crop__help`) — в ПРАВОМ ВЕРХНЕМ УГЛУ ПРЕВЬЮ (внутри
  `.degg-crop__stage`, как в `Degg_Images_Save_Compare`); всплывающая подсказка
  (`.degg-crop__helpbox`) — в корне (сцена режет содержимое, `overflow:hidden`),
  позиционируется под кнопкой через `syncHelpAnchor()`;
  открывается по клику/наведению, текст — `LABELS.help` (RU/EN), включает
  описание Shift-приёмов и координат;
- DRAG-ИНВАРИАНТ: масштаб и смещение сцены фиксируются на `pointerdown`
  (`state.drag.view`) и используются во всех `pointermove`. Иначе рост рамки
  расширяет union → меняет `scale` → следующий `pointermove` считает дельту по
  новому масштабу, и рамка разгоняется до клампа (доля сцены → 88);
- `state.suppress` защищает от реентерабельности: программная запись виджета
  (`programmatic`) не должна вызывать callback'и, которые сами пишут в виджеты;
- язык: `Comfy.Locale` (через `app.extensionManager.setting.get`) → `ru` при
  префиксе `ru`, иначе `en`; словари в `LABELS`; подписи кнопок, combo
  (`getOptionLabel`) и замка (`options.on/off`) переприменяются на событии
  legacy-настроек `Comfy.Locale.change` — без перезапуска ComfyUI;
- публичный API редактора: `node.__deggCrop = { widget, layout, commit, refresh,
  state }` — тестовых хуков нет (проба задаёт кадр через `crop_rect` +
  `refresh()`);
- `onConfigure`/`loadedGraphNode` → `refresh()`; сериализация рамки в `crop_rect`.

## 8. Известные ограничения (решения, оставленные пользователем)

Ниже — то, что осознанно НЕ менялось. Перед «улучшением» сначала сверяйся с
этим разделом: правка поведения требует явного решения пользователя.

### 8.1. Мегапиксели затираются при смене картинки

`resetToImage()` ставит результат = размер изображения, поэтому поле
«Мегапиксели» после сброса показывает площадь картинки (а не то, что было до
смены). Это прямое следствие решения пользователя «значения в ноде принимают
значения изображения».

- Следствие: смена картинки перезаписывает MP; чтобы вернуть «2.0 МП», надо
  вписать MP заново.
- Как изменить, если понадобится сохранять MP: в `resetToImage()` НЕ ставить
  ручной размер (тогда результат останется от MP) либо не трогать MP — но тогда
  поля «Ширина/Высота результата» перестанут показывать размер картинки.
- Проверки, которые придётся поправить: «подключение картинки: результат =
  размер картинки», ««Сбросить»: размер результата = размер изображения»,
  ««Сбросить»: мегапиксели = площадь изображения».

### 8.2. Сервер не использует шесть видимых входов

`aspect_ratio`, `lock_ratio`, `center_x`, `center_y`, `frame_w`, `frame_h` — это
элементы управления редактора; машинное состояние ноды лежит в `crop_rect`
(геометрия кадра) и `output_size` (ручной размер результата). Подробности —
§5.0.

- Следствие: при запуске без браузера (API, headless) эти шесть полей инертны;
  рамка и размер результата берутся только из `crop_rect`/`output_size` (и из
  `megapixels`/`multiplicity`). При этом ComfyUI требует передать их в промпте
  (все обязательные входы), иначе `400 required_input_missing`.
- Почему так: из одних `center_x/center_y/frame_w/frame_h` геометрию кадра
  вывести нельзя — `frame_w/frame_h` это размер РЕЗУЛЬТАТА, а не размер обреза
  в источнике.
- Как изменить: это переработка контракта (сервер сам считает кадр из
  координат и размеров) — ломает ТЗ и требует отдельного решения.

  ✅ Решено 2026-10-21 (без переработки контракта):
  1. эти шесть входов и скрытые `crop_rect`/`output_size` объявлены
     **необязательными** — API их не требует (проверено: запуск через API с
     одними значимыми входами работает, `tests/_check_real_mask.py`);
  2. порядок виджетов на теле ноде задаёт редактор — константа
     `WIDGET_ORDER` в `web/js/crop_image.js` (ComfyUI рисует обязательные
     первыми, поэтому без этого порядок уехал бы);
  3. ⚠️ следствие: фронтенд восстанавливает значения виджетов ПОЗИЦИОННО
     (настройка `Comfy.Workflow.NamedValuesRestore` выключена по умолчанию),
     а порядок виджетов теперь задаёт редактор. Чтобы старые воркфлои не
     разъехались, нода восстанавливает значения **по именам** из
     `info.widgets_values_named` (`restoreWidgetValuesByName`) и подстраховывает
     значения (`sanitizeWidgetValues` — недопустимое значение пропорций → 'free');
  4. проверки: Python-тест (контракт обязательных/необязательных), аудит
     (порядок + восстановление по именам), живая DOM-проба (порядок на теле
     ноды, восстановление по именам, **реальный воркфлоу пользователя** —
     значения встают на свои виджеты);
  5. внешний вид не изменился (снимок живого узла до/после совпадает).


### 8.4. Размер результата при смене картинки: в интерфейсе и в API по-разному

Сброс под картинку (§5, `resetToImage`) выполняет **JS-редактор**, то есть
только когда нода открыта в интерфейсе:

- **в интерфейсе**: подключили картинку → рамка = вся картинка, центр = 0,
  пропорции = пропорции картинки, **разрешение результата = размер картинки**
  (1:1, без ресайза), поле «Мегапиксели» = площадь картинки в единицах ноды
  (1 МП = 1024²; в плашке рядом — истинные мегапиксели, 1 МП = 1 000 000);
- **без браузера (API/скрипт)**: редактора нет → сброса нет → размер
  определяется тем мегапикселем, который передан в промпте. Проверено:
  источник 2720 × 1536 + МП 2.0 → результат 1928 × 1088
  (`tests/_check_image_size.py`).

Это осознанно: в скрипте размер задаёт вызывающий, а нода не гадает, что вам
нужен 1:1 с оригиналом.

✅ Решение пользователя (2026-10-21): **оставить как есть**, ничего не менять.

Если позже понадобится одинаковое поведение в API — вариант: переключатель
«Результат: По мегапикселям / Вручную» (тогда «Вручную» даёт размер = размер
картинки, и в UI, и в API). Вариант с серверным правилом «кадр = вся картинка →
размер = картинки» НЕ рекомендуется: он отключил бы мегапиксели, пока кадр
занимает всю картинку (чтобы получить 2 МП, пришлось бы сначала уменьшить кадр).
